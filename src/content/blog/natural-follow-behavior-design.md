跟随和被跟随在 RPG 中出现得非常频繁：玩家可能要跟着 NPC 前往某个地点交付任务，也可能在探索、护送或同行过程中，由 NPC 一路跟着玩家行动。这是一个会被反复看到的细节，但在我的体验里，目前大多数 RPG 并没有很好地打磨它。

许多跟随功能确实可以完成“跟上目标”或“到达指定地点”的任务，但实际表现往往还是显得生硬、不够灵动：NPC 的起步和停止像在响应指令，转弯和追赶缺少过渡，与玩家的距离和站位也会忽近忽远。功能没有失效，角色的行为却很容易让人出戏。

这些问题不是单纯调高移动速度或缩短跟随距离就能解决的。对跟随系统而言，玩家的行为是一组无法预先控制的外部输入。玩家何时起步、向哪里移动、什么时候加速、转向或停止，都不由跟随系统决定。我们真正能够优化的，是 NPC 面对这些变化时所呈现出来的跟随表现。

自然跟随的目标并不是让 NPC 精确复制玩家的移动，而是让 NPC 在玩家不可预测的行为下，持续维持一种合理、可恢复的空间关系。

在讨论具体规则前，先明确本文的范围。跟随关系可以分成两种：玩家跟随 NPC，以及 NPC 跟随玩家。本文作为上篇，只讨论**玩家作为被跟随方、NPC 作为跟随方**的情况，场景以《原神》一类采用常见 3C（Character、Camera、Control）的 3D 第三人称 RPG 为例。

这里的 NPC 指由行为树和运动控制驱动的游戏角色，不涉及 LLM 或生成式 AI。

这篇文章只围绕三个问题展开：NPC 应该待在哪里，应该什么时候响应，以及应该怎样移动过去。后面的站位区域、状态延迟和运动控制，分别回答这三个问题。

## 1. 先定义自然跟随：追踪关系，不追固定点

如果把“跟随玩家”理解成不断追逐玩家当前的位置，NPC 通常会出现两种问题：要么始终落后，要么为了追上目标频繁加速、刹车和修正。更自然的做法，是让 NPC 维护一个相对玩家变化的站位区域。

这意味着跟随系统不需要每一帧都回答“NPC 应该去哪个固定坐标”，而是依次回答：

1. 玩家当前的状态是什么；
2. NPC 当前是否仍在合理站位区域内；
3. 如果不在，应该向哪个较近的位置恢复；
4. NPC 应该用多快的速度和多大的加速度完成恢复。

后文的规则都服务于这四步。站位区域负责定义“合理”，状态延迟负责定义“什么时候知道”，运动控制负责定义“怎样过去”，行为树只负责切换当前意图。

## 2. NPC 应该待在哪里：从侧后方偏好到有效区域

### 2.1 静止时的默认偏好

当玩家静止时，可以把玩家的侧后方作为 NPC 的默认偏好站位。这里的“侧后方”只是一个容易被玩家找到、也方便继续跟随的起始方向，不是要求 NPC 永远锁定左后方、右后方或正后方某个固定点。

如果 NPC 长期保持一个精确坐标，玩家只要改变朝向，NPC 就可能为了重新占据这个坐标而突然横移，或者绕到玩家另一侧。自然的跟随应该允许站位在一个范围内变化。

### 2.2 用一个区域同时描述角度和距离

NPC 不能离玩家太近，也不能落后到看不见。因此，站位距离应该是一个范围，而不是一个固定值：

```text
距离 d ∈ [Min, Max]
```

在距离范围之外，再加入玩家朝向定义的角度范围，就可以得到一个有效站位区。为了方便推导和制作 Demo，暂时假设有效扇形的角度为 `150°`、最大距离为 `5` 米：

```text
角度 θ ∈ [-75°, 75°]
距离 d ∈ [Min, 5m]
```

这里以玩家身后的中线为 `0°`，`d` 表示 NPC 与玩家之间的距离，`θ` 表示 NPC 相对于这条中线的夹角。`150°` 和 `5m` 是演示参数，不是行为学结论；实际项目中可以根据玩家速度、角色体型、人物关系和表演需求调整。

有效站位区的意义是容许变化：只要 NPC 仍在这个区域内，就不需要强行回到某个坐标。为了避免 NPC 长期贴着边界移动，还可以在有效区内部划出一个更小的偏好区：

- 位于偏好区时，保持当前相对位置；
- 位于有效区内但离开偏好区时，只做轻微修正；
- 完全离开有效区时，才进行明显的站位调整。

因此，“左后方”和“右后方”不应该成为 NPC 的固定状态。它们只是根据 NPC 当前相对玩家的位置计算出来的结果。玩家转向后，NPC 可以自然地从左后方变成右后方，只要它仍然处于新的有效区内，就不需要为了维持原来的站位侧而绕路。

### 2.3 玩家转向时，先判断当前站位是否仍然有效

玩家的朝向变化会让有效扇形一起旋转。小幅转弯时，NPC 原本的位置通常仍然落在新的有效区内，此时只要继续移动，不必重新寻找站位。

如果玩家突然大幅转向，NPC 可能落在新扇形之外。系统这时才需要重新计算目标，目标可以理解为 NPC 当前位置在新有效区中的最近投影点：

```text
下一目标 = NPC 当前位置在新有效区中的最近合理位置
```

由此可以得到三个直观结果：

- 小幅转弯：当前站位仍然有效，不做站位修正；
- 中等转弯：NPC 可以自然地从左后方变成右后方；
- 大幅转弯：当前站位失效，向新有效区恢复。

转弯结果不是由一个固定的左右站位决定的，而是由新的目标方向、NPC 当前速度和双方的相对位置共同形成。

## 3. NPC 什么时候响应：延迟状态与实时安全通道

### 3.1 玩家先动，NPC 稍后响应

玩家开始移动时，NPC 不必在同一帧立刻起步。更自然的表现是：玩家先动，NPC 经过一个短暂的反应延迟后再跟上。这个延迟模拟的是 NPC 观察到玩家状态变化后作出响应的过程。

延迟不只用于起步，也用于之后对玩家速度、方向和转向状态的同步。NPC 不应该复现玩家走过的精确路径，而应该在获得玩家状态后，结合自己的当前位置重新计算下一目标。

这里需要区分三个时间概念：

- **移动确认时间**：判断玩家是在正式移动，还是只进行了很小的操作；
- **状态采样间隔**：系统多久记录一次玩家状态，属于工程实现频率；
- **反应延迟 `τ`**：玩家状态确认发生变化后，NPC 在表现上晚多久响应。

本文所说的“状态延迟”主要指第三项。移动确认可以过滤短暂的微调，状态采样负责形成连续记录，三者不应该被简单相加成一段漫长等待。

行为学实验也观察到了类似滞后。在一项直线行人跟随实验中，领路者改变速度后，跟随者加速度变化的平均延迟约为 `420ms`。这说明“玩家先动、NPC 稍后响应”具有现实依据，但并不意味着游戏中的延迟参数应该直接设置为 `420ms`；实际取值仍然要服从角色响应感、移动速度和动画节奏。[行人跟随中的速度视觉控制研究](https://pmc.ncbi.nlm.nih.gov/articles/PMC3919103/)

### 3.2 延迟不能覆盖紧急距离判断

跟随系统可以用延迟状态驱动普通跟随，但不能用延迟状态处理所有问题。正常跟随使用玩家的延迟状态快照：

```text
玩家状态快照
= 位置 + 移动方向 + 移动速度 + 转向状态
```

与此同时，系统还要使用玩家当前的真实位置检查双方距离。这个不经过延迟的安全通道只负责判断是否需要进入 `CatchUp` 或 `Recover`，不会直接驱动普通跟随动作。

这样可以同时得到两种效果：普通状态下保留“玩家先动、NPC 稍后跟上”的自然感，玩家突然加速或双方距离失控时，又不会因为等待延迟而让 NPC 落后太久。

这也得到一项人机跟随实验的间接支持：相比复现被跟随者的精确路径，参与者认为朝向被跟随者当前方向移动的机器人更加自然、更像人。[Natural Person-Following Behavior for Social Robots](https://www.ri.cmu.edu/pub_files/pub4/gockley_rachel_2007_1/gockley_rachel_2007_1.pdf)

## 4. NPC 怎么移动：从目标区域到连续运动

把前面的规则串起来，跟随系统每次更新时可以按下面的顺序工作：

```text
读取玩家的延迟状态
→ 判断 NPC 当前站位是否合理
→ 计算站位目标
→ 得到参考移动速度
→ 通过加速度逐渐执行
```

### 4.1 根据有效区域计算下一目标

在时间 `t`，系统同时拥有玩家的延迟状态与 NPC 的当前状态：

```text
玩家的延迟状态 Sₚ(t - τ)
= 位置 Pₚ + 速度 Vₚ + 朝向 φₚ

NPC 的当前状态 Sₐ(t)
= 位置 Pₐ + 速度 Vₐ + 运动朝向 φₐ
```

先把 NPC 当前的世界坐标转换到玩家延迟状态的局部坐标，得到距离 `d` 和相对角度 `θ`，再选择期望相对位置 `r*`：

```text
NPC 位于偏好区：r* 保持当前相对位置
NPC 位于有效区但离开偏好区：r* 指向较近的偏好位置
NPC 位于有效区外：r* 指向有效区中的最近合理位置
```

`r*` 仍处于玩家局部坐标中，需要转换为世界坐标中的站位目标 `Q`：

```text
Q = Pₚ(t - τ) + Rotate(φₚ(t - τ), r*)
```

当玩家大幅加速、NPC 严重落后时，目标选择可以暂时优先缩短实际距离，而不必坚持理想的侧后方角度。回到有效区后，再逐渐整理站位。

### 4.2 用参考速度和加速度完成移动

根据玩家的延迟速度和站位误差，可以得到 NPC 的参考速度：

```text
Vraw = Vₚ(t - τ) + Kₚ(Q - Pₐ)
Vᵣ = ClampMagnitude(Vraw, Vₘₐₓ(state))
```

其中，`Vₚ(t - τ)` 负责同步玩家的延迟运动，`Kₚ(Q - Pₐ)` 负责逐渐消除 NPC 与合理站位之间的误差，`Vₘₐₓ(state)` 允许正常跟随和追赶状态使用不同的最高速度。

参考速度不能直接设置给 NPC，否则速度会突然改变。实际执行时，系统应该持续施加加速度，让当前速度逐渐接近参考速度：

```text
Aₐ = ClampMagnitude((Vᵣ - Vₐ) / T, Aₘₐₓ(state))

Vₐ(t + Δt) = Vₐ(t) + Aₐ × Δt
Pₐ(t + Δt) = Pₐ(t) + Vₐ × Δt
```

`T` 控制速度收敛需要多长时间，`Aₘₐₓ(state)` 限制不同状态下的最大加速度。代码实现上，跟随系统持续给 NPC 设置加速度或移动输入，而不是在状态变化时直接把速度改成目标值。

因此，跟随的自然感来自一个连续过程：

```text
延迟读取状态 → 计算站位目标 → 速度逐渐接近 → 站位最终收敛
```

同一套控制也会自然产生不同的转弯表现：目标方向变化较小时，参考速度方向变化较小，NPC 会走出平缓的弯；目标方向变化较大时，NPC 会逐渐提高转向幅度。速度越高，完成同样转向所需的空间越大，因此还需要通过状态对应的速度和加速度上限限制追赶时的转弯幅度。

时间延迟可能带来追过头和反复修正。加速度收敛可以提供一定的阻尼，但最终是否稳定，仍取决于延迟时间 `τ`、站位修正系数 `Kₚ`、速度收敛时间 `T` 以及速度和加速度上限的组合。[Time-delayed Follow-the-Leader model](https://www.aimsciences.org/article/doi/10.3934/nhm.2015.10.579)

## 5. 优先级与行为树状态

当多个目标发生冲突时，跟随系统需要先决定什么更重要。本文采用下面的优先顺序：

```text
保证跟得上
> 回到有效站位区
> 回到偏好站位区
> 追求理想的侧后方角度
```

这意味着严重落后时，NPC 可以暂时放弃理想角度，先缩短距离；回到有效区域后，再逐渐整理站位。

行为树决定 NPC 当前的跟随意图，运动控制模型决定 NPC 具体“怎么走过去”。将前面的规则落到行为树后，可以得到一组简单的跟随状态：

| 状态 | 进入条件 | 当前意图 |
| --- | --- | --- |
| `Idle` | 玩家与 NPC 均已静止 | 保持静止偏好站位 |
| `React` | 玩家移动意图得到确认 | 等待反应延迟并准备起步 |
| `Follow` | 反应延迟结束 | 执行有效区判断与加速度控制 |
| `CatchUp` | 当前真实距离超过 `Max` | 暂时提高最高速度和加速度，优先缩短距离 |
| `Settle` | 玩家停止，而 NPC 尚未完成收尾 | 逐渐减速并回到静止偏好区 |
| `Recover` | 距离或导航状态进入兜底阈值 | 使用项目定义的方式恢复跟随关系 |

主要的状态转换关系为：

```text
Idle → React：玩家移动意图得到确认
React → Follow：反应延迟结束
React → Idle：玩家在延迟期间又停止
Follow → CatchUp：当前真实距离超过 Max
CatchUp → Follow：当前真实距离回到有效范围
Follow / CatchUp → Settle：玩家停止
Settle → Idle：NPC 完成减速与站位收尾
任意状态 → Recover：距离或导航状态进入兜底阈值
Recover → React / Idle：跟随关系恢复
```

这些状态不直接设置 NPC 的位置或速度，只切换当前的跟随意图。具体运动仍然由前面的目标生成和加速度控制完成。

## 6. 用一个完整过程检查设计是否连贯

把玩家的一次“起步—加速—转弯—停止”串起来，系统行为应该是这样的：

1. **玩家静止**：NPC 位于侧后方偏好区，保持当前相对位置。
2. **玩家开始移动**：系统先确认这是正式移动，NPC 使用延迟状态进入 `React`，不会同帧弹起。
3. **玩家持续前进**：延迟结束后进入 `Follow`，NPC 根据延迟位置和速度计算目标，再通过加速度逐渐跟上。
4. **玩家突然加速**：普通跟随仍使用延迟状态，但实时距离通道发现 NPC 正在落后，状态切换到 `CatchUp`，优先缩短距离。
5. **玩家转弯**：有效站位区随玩家延迟朝向旋转。若 NPC 仍在区域内，就从当前位置继续走；只有离开区域时，才向新的最近合理位置修正。
6. **玩家停止**：NPC 进入 `Settle`，先完成减速，再回到静止时的偏好区，最后回到 `Idle`。

这个过程同时解释了开头提到的几种生硬表现：延迟和加速度处理起步、停止与追赶，动态站位区处理距离和角度，行为树则决定当前优先执行哪一种意图。

## 小结

这套跟随设计可以归纳为三条原则：

1. 自然跟随不是追逐一个固定点，而是维护一个允许变化、能够恢复的动态空间关系。
2. NPC 不复现玩家走过的精确路径，而是在延迟读取玩家状态后，根据自己的当前位置重新计算下一目标。
3. 行为树负责切换 NPC 的跟随意图，运动控制负责把意图转化为连续的移动表现。

本文讨论的是 NPC 跟随玩家的情况。当玩家成为跟随方时，设计目标会从“维持自然站位”转变为“让 NPC 提供清晰、可追踪的引导”，这部分留到下篇继续讨论。
