跟随和被跟随在 RPG 中出现得非常频繁：玩家可能要跟着 NPC 前往某个地点交付任务，也可能在探索、护送或同行过程中，由 NPC 一路跟着玩家行动。这是一个会被反复看到的细节，但在我的体验里，目前大多数 RPG 并没有很好地打磨它。

许多跟随功能虽然能让 NPC 跟上目标，但表现常常比较生硬：起停像在执行指令，转弯和追赶缺少过渡，距离和站位也不够稳定。调高移动速度或缩短跟随距离并不能解决这些问题。因为玩家何时起步、加速、转向或停止都无法预知，系统能控制的只有 NPC 如何回应。
这是系列的上篇，只讨论 NPC 跟随玩家的情况。当玩家成为跟随方时，设计目标会从“维持自然站位”转变为“让 NPC 提供清晰、可追踪的引导”，那部分留到下篇。



## 1. 设计概览：一个会呼吸的扇形

我想要的跟随更像放风筝：玩家始终牵着线，但 NPC 有自己的滑翔。具体来说，我不让 NPC 锁定玩家身后的某个固定点，而是给它一个**会随运动状态变形的扇形区域**：走得慢，待在侧后方；玩家突然跑起来，NPC 先愣一下再追，位置被拉向正后方；玩家停下，再慢慢踱回侧后方。

## 2. 站位：扇形模型

### 2.1 静止/怠速时，待在侧后方

玩家在城里慢走、停下来看风景的时候，NPC 最自然的位置不是正背后——那更像尾随——而是侧后方。

低速稳定状态下，NPC 的理想站位位于玩家坐标系的第三、第四象限，也就是左后方或右后方。它可以缓速跟进，与玩家维持近似稳定的相对位置。

### 2.2 速度变化时，扇形会“呼吸”

玩家突然加速跑起来时，NPC 因为反应延迟会短暂落后，相对位置被拉向中轴；进入追赶后，理想站位也主动向中轴收拢——收成一条缝的扇形让 NPC 可以走直线、跑得快。玩家减速停下后，理想站位再重新展开回侧后方。

这些随运动状态连续变化的理想站位，在玩家身后共同形成一个扇形。

距离也会随状态变化。静止时靠近 `Min`，低速移动时位于 `Min` 和 `Max` 之间，高速追赶时再向 `Max` 拉开。

## 3. 时序：玩家先动，NPC 稍后响应

### 3.1 反应延迟：跟随的“人味”来源

玩家在起步的同一帧就被跟上，看起来会很机灵，但也很不像人。我选择让 NPC 先观察、再响应：玩家先动，NPC 经过一段反应延迟 `τ` 后再跟上。这个延迟模拟的是 NPC 注意到玩家状态变化、再作出反应的过程。

延迟不只用于起步，玩家速度、方向和朝向的变化也应稍后传给 NPC。日式 RPG 常见的“蜈蚣式跟随”让队员复现领队路径，转弯时像一列火车。我的做法是让 NPC 根据延迟后的玩家状态和自身位置**重新计算目标**，而非复现路径。研究也表明，相比精确复现路径，朝向被跟随者当前方向移动的机器人更自然。[Natural Person-Following Behavior for Social Robots](https://www.ri.cmu.edu/pub_files/pub4/gockley_rachel_2007_1/gockley_rachel_2007_1.pdf)

一项直线行人跟随实验显示，领路者改变速度后，跟随者加速度变化的平均延迟约为 `420ms`。这可作为“玩家先动、NPC 后响应”的现实参照，但不能直接照搬进游戏。`τ` 仍需根据角色响应感、移动速度和动画节奏调整。[行人跟随中的速度视觉控制研究](https://pmc.ncbi.nlm.nih.gov/articles/PMC3919103/) `τ` 越长，NPC 越从容，也越容易掉队；距离失控时，实时安全通道会立即触发追赶。

</figure>

工程上有三个容易混淆的时间概念。它们不能简单相加，否则 NPC 会等得太久：

- **移动确认时间**：判断玩家是正式移动，还是只碰了一下摇杆，也是第 5 节 `React` 状态的进入条件；
- **状态采样间隔**：系统多久记录一次玩家状态，纯属实现频率；
- **反应延迟 `τ`**：玩家状态确认变化后，NPC 在表现上晚多久响应，本文讨论的“延迟”都指它。

### 3.2 超出边界后追赶

偶尔有常见边界情况，例如玩家突然释放了位移技能。
所以系统同时维护两条通道：

- **延迟快照**：玩家的位置、移动方向、移动速度、转向状态，经过延迟后驱动普通跟随；
- **实时通道**：只用玩家当前的真实位置检查双方距离，一旦超过 `Max` 或距离失控，立刻触发追赶；除此之外不参与普通跟随。

普通情况下，NPC 仍会晚一步响应；距离超过 `Max` 时，实时通道会直接切入追赶，不再等待延迟。

## 4. 运动：从站位目标到连续移动

### 4.1 把运动状态翻译成扇形内的理想站位

系统每次更新时，手里有两份状态：玩家的延迟状态 `Sₚ(t - τ)`（位置 `Pₚ`、速度 `Vₚ`、朝向 `φₚ`），以及 NPC 的当前状态 `Sₐ(t)`。

先把 NPC 的世界坐标转换到玩家延迟状态的局部坐标，得到当前距离 `d` 和相对角度 `θ`。再用 `u ∈ [0, 1]` 表示当前的追赶强度。`u` 可以由玩家延迟速度归一化后与距离误差加权得到，Demo 里甚至可以只用速度一项。理想站位可以这样计算：

```text
θ_pref = side × Lerp(θ_side, 180°, u)
d_pref = Lerp(Min, Max, u)
```

**跑得越急，越往正后方钻，也离玩家越远**。`side` 表示当前位于左侧还是右侧（它只是结果，不是状态），`θ_side` 是静止时从玩家前向量到侧后方的偏好角度。`u = 0` 时，NPC 靠近侧后方的 `Min`；`u = 1` 时，NPC 靠近中轴上的 `Max`。

玩家沿自己的朝向跑远时，落后的 NPC 本来就会自然接近正后方，因此 `|θ|` 向 `180°` 靠拢有一半是几何白送的。`θ_pref` 负责几何不会自动完成的另一半：减速后重新展开到侧后方，以及左右侧的选择与切换。这些几何不送。

`d_pref` 与 `θ_pref` 共同得到局部坐标中的理想站位。站位周围设一小块容差区防抖：NPC 位于容差区内时保持当前相对位置，离开后目标指向扇形内较近的一侧。最后把局部目标转换回世界坐标：

```text
Q = Pₚ(t - τ) + Rotate(φₚ(t - τ), r*)
```

玩家转向后，延迟朝向会带着整个扇形一起旋转。系统不要求 NPC 复现玩家刚走过的轨迹，也不预先锁死左右侧，而是在新扇形中分别计算两个候选目标：一个保留 NPC 当前所在侧，另一个位于相反侧。两个目标都要符合当前速度对应的理想角度和距离，并且能够通过导航到达。

接着比较 NPC 从当前位置到两个候选目标的移动代价。为了避免轻微转向时反复换侧，换侧候选需要额外加一项切换代价 `H_side`：

```text
C_same   = PathCost(Pₐ, Q_same)
C_switch = PathCost(Pₐ, Q_switch) + H_side
Q = Q_switch if C_switch < C_same, otherwise Q_same
```

开阔区域中的 `PathCost` 可以先用直线距离，接入导航后再换成可达路径长度。`H_side` 只提供换侧滞后，不会把 `side` 变成行为树中的离散状态。

小幅转弯时，新扇形只旋转了一小段，原侧目标通常仍然更近。NPC 会保留原侧，从转弯外侧走出一条较大的弧线。玩家大幅转弯后，旧站位可能已经靠近新扇形的另一侧；如果内切路径在加上 `H_side` 后仍然更短，NPC 就直接穿过转弯内侧，换到另一侧，用小弯接上玩家，而不是照着玩家的轨迹绕大弯。

因此，系统不是按转弯角度硬切两种模式。转弯幅度会改变扇形的位置，NPC 的当前站位、速度和导航代价则共同决定最终是沿外弧保留原侧，还是内切换边。

### 4.2 用参考速度和加速度走完最后一步

站位目标有了，接下来是怎么走过去。根据玩家的延迟速度和站位误差，得到 NPC 的参考速度：

```text
Vraw = Vₚ(t - τ) + Kₚ(Q - Pₐ)
Vᵣ = ClampMagnitude(Vraw, Vₘₐₓ(state))
```

NPC **一边跟上玩家的延迟速度，一边按站位误差纠偏**；`Vₘₐₓ(state)` 允许正常跟随和追赶状态使用不同的速度上限。

参考速度不能直接赋值，否则速度会瞬间跳变。我选择让系统持续施加加速度，让当前速度逐渐接近参考速度：

```text
Aₐ = ClampMagnitude((Vᵣ - Vₐ) / T, Aₘₐₓ(state))

Vₐ(t + Δt) = Vₐ(t) + Aₐ × Δt
Pₐ(t + Δt) = Pₐ(t) + Vₐ × Δt
```

`T` 控制收敛需要多长时间，`Aₘₐₓ(state)` 限制不同状态下的最大加速度。代码层面，跟随系统持续输出加速度或移动输入，不在状态变化时直接改写速度。起步和停止因此有了过渡，动画系统也更容易配合。

同一套控制也能处理转弯。目标方向变化小，参考速度的方向变化也小，NPC 会走出平缓的弯。变化大时，转向幅度逐渐提高。速度越高，完成转向所需的空间越大，因此还要用各状态的速度与加速度上限约束追赶时的转弯幅度。

延迟加修正增益的组合本身有振荡风险：追过头、再反向修正、来回拉锯。加速度收敛可以提供阻尼，但最终是否稳定，仍取决于 `τ`、`Kₚ`、`T` 以及各项上限的搭配。[Time-delayed Follow-the-Leader model](https://www.aimsciences.org/article/doi/10.3934/nhm.2015.10.579)

## 5. 整合：优先级与行为树

多个目标冲突时，需要先决定什么更重要：**保证跟得上 > 回到扇形范围 > 收敛到当前状态的理想角度 > 停止后整理回侧后方**。

行为树决定 NPC 当前的跟随意图，以及各状态下的速度、加速度上限；连续运动始终由第 4 节的控制模型完成。两套“状态”的关系是：行为树是离散的意图层，`u` 和 `θ_pref` 是每一层内部连续变化的量。

| 状态 | 进入条件 | 当前意图 |
| --- | --- | --- |
| `Idle` | 玩家与 NPC 均已静止 | 保持静止偏好站位 |
| `React` | 玩家移动意图得到确认 | 等待反应延迟并准备起步 |
| `Follow` | 反应延迟结束 | 根据当前速度调整扇形内的理想角度与距离 |
| `CatchUp` | 当前真实距离超过 `Max` | 提高速度和加速度，并让目标角度向中轴收拢 |
| `Settle` | 玩家停止，而 NPC 尚未完成收尾 | 逐渐减速，并把目标位置展开回侧后方 |
| `Recover` | 距离或导航状态进入恢复阈值 | 使用项目定义的方式恢复跟随关系 |

## 小结

本文采用的方案如下：

| 决策点 | 备选方案 | 本文选择 | 理由 |
| --- | --- | --- | --- |
| 跟随策略 | 复现玩家路径（蜈蚣式） | 目标重算 | 转向自然，有文献支持 |
| 响应时机 | 即时响应 | 反应延迟 + 实时安全通道 | 从容感与掉队恢复兼得 |
| 速度执行 | 直接设置速度 | 加速度收敛 | 无速度跳变，对动画系统友好 |
| 站位约束 | 固定点、固定侧 | 动态扇形 | 随速度变形，转向可顺势换侧 |


下篇将换一个方向：当玩家成为跟随方时，设计目标会从“维持自然站位”转变为“让 NPC 提供清晰、可追踪的引导”，届时再讨论领队 NPC 的行为设计。
